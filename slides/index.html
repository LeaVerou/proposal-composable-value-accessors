Is “accessor” the right framing?

For the simple case, accessors are an implementation detail.

  • User intent is not "I want an accessor" unless there is logic.
- Just like functions are an implementation detail for classes and we didn't design class syntax around them - TAG anecdote

Problem statements

  1. We need a high signal-to-noise ratio way to define data properties that become part of the class shape
  2. Additive accessor use cases are common enough to deserve better signal-to-noise ratio

Why solve them together?

  • Class public data properties often evolve into additive accessors
  • Solving them together productively constrains the solution space and avoids language clutter

Never accessed outside the accessor

						#foo = 1;
						get foo () { return this.#foo; }
						set foo (v) { this.#foo = v; }
					}
				

					class C {
						_foo = 1;
						get foo () { return this._foo; }
						set foo (v) { this._foo = v; }
					}
				

					class C {
						[foo] = 1; // symbol
						get foo () { return this[foo]; }
						set foo (v) { this[foo] = v; }
					}
				

				class C {
					propertydata foo = 1;
				}
